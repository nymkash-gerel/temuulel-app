## ХЭСЭГ A — Sub-agent-ууд (хамгийн тод техникийн цоорхой)

### A.1 Яагаад чухал вэ

Хичээл sub-agent-ыг маш их онцолсон. Гол санаа: **тусдаа context цонхтой, хязгаарлагдмал tool-той, хямд загвартай** туслах агент. 5 шалтгаан:

1. **Context хамгаалах** — 273 route-той энэ хэмжээний кодод үндсэн session context хурдан дүүрдэг. Sub-agent тусдаа цонхонд ажиллаад зөвхөн үр дүнг буцаана (хичээлд: sub-agent 40k токен зарсан ч үндсэн session 29k хэвээр үлдсэн жишээ).
2. **Tool хязгаарлах** — security шалгагчид зөвхөн read-only эрх өгч, санамсаргүй өөрчлөлтөөс сэргийлнэ.
3. **Тохиргоо дахин ашиглах** — нэг тодорхойлсон агентыг session бүрт дахин ашиглана.
4. **Мэргэшил** — нэг агент нэг л нарийн ажил ("tiny agents win").
5. **Зардал хэмнэх** — энгийн ажлыг Haiku/хямд загварт даалгана.

### A.2 Тэмүүлэлд хийх ёстой тодорхой агентууд

`.claude/agents/` хавтас үүсгээд дараах агентуудыг бий болго. Файл бүр YAML frontmatter + заавартай.

#### (1) `security-auditor.md` — deploy бүрийн өмнөх аюулгүй байдлын шалгалт

Таны git log-д саяхан `security: fix audit findings (1 critical, 6 high, 12 medium, 5 low)` гэсэн commit байсан. Энэ шалгалтыг **тогтмол, автомат** болго.

```markdown
---
name: security-auditor
description: Тэмүүлэлийн deploy-оос өмнө RLS, service-role, rate-limit, secret задралыг шалгана. Read-only.
tools: Read, Grep, Glob, Bash
model: sonnet
---

Чи бол Тэмүүлэл SaaS-ийн аюулгүй байдлын аудитор. Дараахыг ШАЛГА (засварлаж БОЛОХГҮЙ, зөвхөн тайлагна):

1. **RLS**: `supabase/migrations/` дахь шинэ хүснэгт бүр RLS policy-тэй эсэх. store_id баганагүй хүснэгт байвал улаан туг.
2. **Service-role урвуулга**: `SUPABASE_SERVICE_ROLE_KEY` client-side код руу алдагдаагүй эсэх. Зөвхөн server-side (`src/lib/supabase/server.ts`)-д хэрэглэгдсэн эсэх.
3. **Rate limit**: `src/app/api/**/route.ts` дахь public/auth endpoint бүр `src/lib/rate-limit.ts` эсвэл Upstash-аар хамгаалагдсан эсэх. Хамгаалалтгүй route-уудыг жагсаа.
4. **Secret задрал**: hardcode хийсэн API key, token, webhook URL байгаа эсэх.
5. **Auth**: mutation бүр `supabase.auth.getUser()`-ээр батлагдсан, client-ийн дамжуулсан user ID-д итгээгүй эсэх.

Гаралт: severity (critical/high/medium/low) тус бүрээр эрэмбэлсэн жагсаалт, файл:мөр заасан, засах зөвлөмжтэй.
```

## ХЭСЭГ D — Context management ба ажлын хэв маяг

Эдгээрийг та ихэвчлэн аль хэдийн мэддэг байх, гэхдээ том кодод онц чухал:

## ХЭСЭГ E — Борлуулалтын систем (хамгийн үнэ цэнтэй хэсэг)

Апп чинь **бэлэн болсон** — цоорхой нь код биш, **үйлчлүүлэгч**. Хичээлийн 5, 6-р бүлэг бүхэлдээ энэ тухай. SaaS-д тохируулан:

### E.1 Нийш ба анхны яриа (LRP арга)

- **Нийш сонгох шүүлтүүр:** 7 хоног тутам давтагддаг процесстой, хурдан төлж чаддаг, чи хэлийг нь ойлгодог салбар. Тэмүүлэл 24 vertical дэмждэг ч, эхлээд **1-2 vertical дээр төвлөр** (жишээ нь ресторан + гоо сайхны салон — FB-ээр их захиалга авдаг, чат ачаалал өндөр).
- **LRP ярилцлага (Сонс–Давт–Шалга):** 5-10 SMB-тэй уулз. "Сонс" = өдрийн ажлыг нь асуу; "Давт" = буцааж хэлж баталгаажуул; "Шалга" (poke) = тоон дээр гарга:
  - "7 хоногт FB мессежид хэдэн цаг зарцуулдаг вэ?"
  - "Хариулдаг хүний цагийн үнэ хэд вэ?"
  - "Шөнө/амралтын өдөр хариулаагүйгээс хэдэн захиалга алддаг вэ?"

### E.2 Үнийн тооцоо (бодит Монгол тоогоор)

Жишээ: нэг ресторан/дэлгүүр FB чатад өдөрт ~4-5 цаг зарцуулдаг ажилтантай гэвэл:

| Хэмжигдэхүүн | Тооцоо |
|---|---|
| Чатбот хариулах хувь | ~70% асуултыг автоматаар |
| Хэмнэсэн цаг | ~3 цаг/өдөр ≈ 90 цаг/сар |
| Ажилтны цагийн үнэ | ~10,000₮/цаг гэвэл |
| **Сарын хэмнэлт (хөдөлмөр)** | **~900,000₮/сар** |
| Нэмэлт: шөнийн захиалга барих | Алдагдаж байсан борлуулалт эргэж |

**Үнэ тогтоолт:** SaaS тул захиалгын шатлал. Хичээлийн "үр дүнгийн хэсэг" логикоор — сарын хэмнэлт ~900k₮ бол:
- **Starter ~99,000₮/сар** (1 суваг, үндсэн чатбот)
- **Pro ~199,000-299,000₮/сар** (олон суваг, image/voice, analytics, white-label)
- Анкор: "Сард ~900,000₮-ийн цаг хэмнэнэ + шөнийн захиалга барина — үнэ нь түүний 1/4 ч хүрэхгүй."

Цагаар биш, **үр дүнгээр** зар: "GPT-4o чатбот" биш → "ажилтан хариулж байсан 5 цагийг автоматжуул, 24 цаг захиалга аваад бай."

### E.3 90 минутын proof-of-concept (POC)

Хичээлийн арга — үйлчлүүлэгч бүрд:
- 15 мин: процессын зураглал (одоо хэрхэн чат хариулдаг вэ).
- 60 мин: тухайн SMB-ийн жинхэнэ бараа/цэсээр Тэмүүлэлд store үүсгэж, чатботыг тохируулах (танд аль хэдийн seed/onboarding бэлэн).
- 15 мин: 3 минутын Loom видео (камер асаалттай) — "таны дэлгүүрт ингэж ажиллана" гэж үзүүл.

### E.4 Үйлчлүүлэгч олох 3 суваг

1. **Хүйтэн хандалт:** 1-2 суваг сонго (FB, имэйл). Өдөрт ~30 имэйл/domain (халаасан domain-оор ~500 хүртэл). "30 мин уулзалт" биш "2 минутын Loom" санал болго. Хариу/эерэг/захиалсан/хаасан гэж хэмжиж, эерэг хариу өгсөн загварыг олж давт.
2. **Trojan horse түншлэл:** FB маркетингийн агентууд, POS/түгээлтийн компани, вэб хийдэг хүмүүстэй хамтар — тэдний үйлчлүүлэгч рүү үнэгүй "AI нээлтийн уулзалт" санал болгож, 20% орлого хуваа. (Партнёрын дам үйлчлүүлэгч 46% хурдан хаагддаг.)
3. **Referral "алтан асуулт":** deploy хийснээс 1-2 сарын дараа, сарын үзүүлэлт харуулах уулзалт дээр асуу. (Борлуулагчдын ердөө 11% нь асуудаг ч үйлчлүүлэгчдийн 91% нь өгдөг — Dale Carnegie.)

### E.5 7 хоногийн анхны үйлчлүүлэгчийн төлөвлөгөө

- **Өдөр 1:** сул позиционинг + 20 хүний "итгэлийн газрын зураг" (Google Sheet: таныг мэддэг хүмүүс).
- **Өдөр 2-3:** зарахгүйгээр дулаан яриа өрнүүл.
- **Өдөр 4-6:** хамгийн тод өвдөлттэй нэг SMB-д үнэгүй пилот (POC) хий.
- **Өдөр 7:** maintenance vs өргөтгөлийн сонголт танилцуул, эсвэл testimonial ав.
- Дараа нь давт; зөвхөн баталгаа (proof) цугласны дараа хүйтэн хандалтад шилж.

### E.6 Хүргэлт/гэрээ

- Үйлчлүүлэгч **өөрийн API key/акаунтаа** төлдөг байх (OpenAI, QPay merchant) — таны нэр дээр usage бүү яв.
- Тодорхой "дууссаны тодорхойлолт" (definition of done)-той бичгэн scope — нэмэлт хүсэлтийг V2 backlog руу (ирээдүйн ажлын үр).
- Loom заавар видео, сарын KPI тайлан өөрөө идэвхтэй илгээ.

## ХЭСЭГ F — Аюулгүй байдал ба deploy сахилга

Хичээлийн шууд анхааруулга, Тэмүүлэлд онц хамаатай:

- **Deploy-оос өмнө security review** — E.2-ийн security-auditor sub-agent-аар автоматжуул.
- **Service-role анхаар:** storefront service_role key-ээр уншдаг (RLS тойрдог) — public RLS policy байгаа ч энэ нь жинхэнэ хамгаалалтын зам биш. Sub-agent энэ хэрэглээг тогтмол шалгана.
- **Secret зөвхөн .env-д**, чатад хэзээ ч биш (таны block-secrets, block-echo-env hook аль хэдийн энэ дүрмийг сахиулдаг — маш зөв).
- **Webhook хатууруул** (HTTPS, гарын үсэг шалгах, rate limit, prompt-injection хамгаалалт) — QPay/messenger webhook-уудад.
